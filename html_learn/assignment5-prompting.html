3 提示

将预训练基础模型用于下游任务的第一步是给它提示。基础模型通过预训练学到了广泛的行为，提示是一种轻量方法，可以让其行为更偏向解决任务。后文还会看到，提示选择会影响 RL 动态和探索。

最基本的方法是给出问题，再从模型的下一 token 分布中采样答案；我们称其为 question_only。我们会将它与 r1_zero 比较：后者除了问题，还包含要求模型进行思维链推理的指令 [DeepSeek-AI 等，2025]。

3.1 使用 vLLM 进行推理

除非另有说明，GSM8K 实验使用以下来自 DeepSeek R1-Zero [DeepSeek-AI 等，2025] 的提示，称为 r1_zero：

提示含义：用户提出问题，助手先思考推理过程，再给出答案；推理放在 <think>...</think> 中，答案放在 <answer>...</answer> 中。

该提示位于 cs336_alignment/prompts/r1_zero.prompt。其中 question 是插入的问题，例如前述 Natalia 卖发夹的题目。模型应扮演助手，从思考过程开始生成，因为开头的 <think> 已经包含在提示中；随后以 </think> 结束思考，再在答案标签内生成最终的符号答案，例如 <answer> 4x + 10 </answer>。这些标签便于解析输出并与标准答案比较，也使我们可以在遇到 </answer> 时停止生成。

3.3 评分函数

模型生成回答后，我们需要检查其正确性。数学题带有标准答案，例如 0.5，但模型可以用多种形式表达同一个正确答案，如 <answer> 1/2 </answer> 或 The answer is 0.5.。因此，我们需要一个以模型输出和已知标准答案为输入、返回正确与否的布尔值的答案解析函数。

实验使用近期推理 RL 研究中的一个快速且较准确的解析器 [Z. Liu 等，2025]。对于 r1_zero 提示，奖励函数为 cs336_alignment.drgrpo_grader.r1_zero_reward_fn。question_only 不要求 <think> 和 <answer> 标签，应使用同文件中的 cs336_alignment.drgrpo_grader.question_only_reward_fn；它会在 \boxed{} 中寻找最终答案。

这些函数返回总奖励，以及独立的格式奖励和答案奖励，分别表示是否符合预期格式、解析出的答案是否正确。有些研究对格式正确但答案错误的回答也给部分分数，即非零总奖励。本实验不给部分分：总奖励就是答案奖励，格式奖励仅用于日志记录。

注意，ground_truth 参数应只包含最终答案。GSM8K 的答案字段格式为 {rationale} #### {answer}，因此应按 #### 分割，并去掉答案两端空白。

1．这项实验要做什么？

总体流程是：读取 GSM8K → 用提示模板包装问题 → 请求模型生成 → 调用评分函数 → 保存输出、统计指标并人工分析。vllm_utils.py 提供的是其中的服务管理和生成接口；读取数据、构造三种提示、评分统计等评估逻辑，需要另外编写。

本节使用固定权重的 allenai/OLMo-2-0425-1B 基础模型，比较 question_only、r1_zero 和 r1_zero_three_shot。这一阶段只做推理和评估，不更新模型参数。详细采样要求与交付内容见上面的 3.4 实验。

2．为什么 vllm_utils.py 不只有启动服务？

这个文件同时为当前推理实验和后面的 RL 训练提供辅助功能。阅读时先分清三组代码：

功能函数或类型本节如何使用
服务生命周期start_server、wait_for_server、stop_server、kill_existing_vllm_server启动、等待就绪、停止服务；也可以先手动启动。
请求生成_http_json、generate_completions、VLLMCompletion提交提示，接收生成文本等结果。
训练后的权重同步init_weight_sync、sync_policy_weights当前可以跳过；以后训练参数更新时再处理。

VLLMServer 把这些函数包装成一个对象。创建 VLLMServer(...) 只记录模型、端口等配置；调用 server.start() 才会尝试启动服务。

command 是在 Python 进程里面执行的吗？

由 Python 发起执行，但 vLLM 服务运行在独立的子进程里。command = ["vllm", "serve", ...] 只是一个字符串列表，保存可执行程序及其参数；执行到 subprocess.Popen(command, env=env, start_new_session=True) 时，操作系统才会创建并启动 vLLM 子进程。原来的 Python 进程继续执行，随后通过健康检查等待服务就绪。

调用链是：server.start() → start_server() → subprocess.Popen(command, ...) → vLLM 子进程。这里说的是默认的 launch_server=True 模式。只创建对象而没有调用 start()，不会执行这条启动链。

手动在终端执行 vllm serve ... 也能启动服务，此时由终端的 shell 发起。两种方式都可以；已有手动启动的服务时，Python 可使用 launch_server=False 连接它。

展开：start() 和生成函数内部具体做了什么？

server.start() 在默认配置下先调用 kill_existing_vllm_server()，尝试清理匹配该端口的旧 vLLM 服务；然后由 start_server() 使用 subprocess.Popen() 启动新进程；最后由 wait_for_server() 反复访问 /health，等模型加载完成、服务可以接收请求。

generate_completions() 把提示和采样参数组织成 JSON，通过 _http_json() 向 /v1/completions 发送 HTTP 请求，再把返回结果整理为 VLLMCompletion。其中 text 是生成文本，token_ids 是生成的 token ID，finish_reason 说明为什么停止生成。batch_size 控制一次 HTTP 请求提交多少条提示。

展开：为什么后面还要同步权重？

评估脚本与 vLLM 服务是独立进程。以后做 RL 时，训练进程会更新自己的模型参数，vLLM 仍持有先前加载的参数。权重同步代码负责把更新后的参数传给 vLLM，并清理旧权重对应的缓存。当前实验模型不变，因此不需要调用这部分函数，也不需要启用 NCCL 权重传输。

为什么 backend 改成 nccl 或 hccl 都报错？

本机的问题出在命令行参数解析阶段。当前安装的是 vllm==0.11.0+empty 和 vllm-ascend==0.11.0rc1。已分别用两个 backend 值实际执行 CLI 参数解析，两次均以退出码 2 结束，模型尚未开始加载：

需要依次区分三层：CLI 是否识别 --weight-transfer-config → 该版本是否注册了指定 backend → backend 使用什么通信实现。本机在第一层就退出了，因此替换 JSON 中的 backend 值无法解决。

你记得的兼容机制有依据：官方仓库的 Ascend 权重上传设计说明 描述了针对 vLLM 0.20.2，将 nccl 注册项映射到 HCCLWeightTransferEngine 的适配方案；当前 RL 文档 则展示直接指定 hccl。这些机制取决于对应版本的实现，不能套用到 0.11.0，也不能据此认定任意版本都可互换两个名称。

ASCEND_RT_VISIBLE_DEVICES 负责指定可见 NPU；后端映射由 Ascend 插件的注册或补丁实现。设置设备变量不会让旧版 vLLM 自动获得新的 CLI 参数。

当前提示实验只做固定模型推理，暂时注释 --weight-transfer-config 及其下一项 JSON 值即可；不需要为了这一节升级整套环境。后续 RL 需要同步训练权重时，再按实际版本选择同步方案。本次排查未修改 Python 代码。

以后怎样改成让 Python 自动启动？

先在原服务终端按 Ctrl+C 停止手动启动的服务，再把示例中的 launch_server=False 改为 True，调用 server.start()。此时会使用 NPU 分支创建服务进程，并等待健康检查通过。任务结束后调用 server.stop()。

原有的 start() 在自动启动前会清理匹配端口的旧服务。因此在已有手动服务上做客户端验证时，应使用 launch_server=False。

此前验证记录（针对移除 max_model_len 前的版本）：通过模拟子进程启动检查了 NPU 的设备变量、上下文长度和移除 NCCL 配置，也检查了 CUDA 配置仍保留原有行为。实际使用 launch_server=False 连接当前服务，并通过 generate_completions() 成功获取了一条 16-token 回答及 token ID。验证期间没有重启现有服务；修改后的自动启动路径尚未实际启动新模型进程。

NPU 适配目前覆盖固定权重的服务启动；后续 RL 的权重同步仍需单独实现。在 NPU 配置下调用 init_weight_sync() 会明确提示当前 NCCL/CUDA 同步路径不可用。
